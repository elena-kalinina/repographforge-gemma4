# RepoGraphForge — Why Training Is Failing, and How to Fix It

Review date: 2026-11-07. Scope: `src/`, `notebooks/repographforge_clean_master.md`,
`notebooks/repographforge_data_preparation.md`, `submission/agent.yaml`.

**Summary:** the pipeline has five independent defects, any *one* of which is enough to
produce "no patch submitted" on nearly every task. They compound. The two that must be
fixed first are the end-of-turn masking bug (B1) and the inverted SFT label (A1).

---

## A. The training data teaches the wrong thing

### A1. CRITICAL — The SFT target is the bug-introducing diff, not the fix

`src/task_synthesizer.py:34` defines the field:

```
"bug_patch": "Valid unified git diff that introduces the bug into the working code."
```

`src/teacher_rollouts.py:81,91` then feeds that exact field to the teacher as the answer:

```python
patch = task.get("bug_patch", "")[:2000]
...
f"### Reference Fix Patch:\n{patch}\n\n"
```

The same inversion is in the notebook, Cell 8 of `repographforge_data_preparation.md`:

```python
patch = task["bug_patch"][:2000]
...  f"### Reference Fix:\n{patch}\n"
```

Every SFT trajectory is therefore a demonstration of *applying the defect*. The model is
being optimised to emit diffs that break code. This alone explains "a patch was submitted
but the tests failed".

**Fix.** The synthesiser must emit the *clean → buggy* direction for the task statement and
the *buggy → clean* direction for the label. Two options:
- Cheapest: invert `bug_patch` before using it as the label (swap `+`/`-` on hunk body
  lines, swap the `---`/`+++` headers), and name the field `fix_patch` in the trajectory
  prompt so the mistake cannot recur.
- Better: drop synthetic tasks entirely for the SFT label and use the **115 real
  `train_tasks.jsonl` tasks**, whose `patch` field is the real gold fix with real line
  context. You have 115 ground-truth (problem, gold diff) pairs sitting unused.

### A2. CRITICAL — The synthesiser never sees any source code

Cell 7 / `src/task_synthesizer.py` prompts the teacher with node *names* and edge
*names* only:

```python
nodes = "\n".join(f"- {n['id']} in {n.get('file','repo')}" for n in sub["nodes"])
edges = "\n".join(f"- {e['source']} -> {e['target']}" for e in sub["edges"][:6])
```

No file contents are read. The model is asked to produce a "unified git diff" against code
it has never seen, so every hunk header and every context line is invented. Such a diff
cannot apply to the real repo, and the "reproduction_test" is equally fictional.

**Fix.** Before synthesis, read the actual span for each node (`file` + line range from the
graph node metadata) and put the real code in the prompt. Then *verify* the generated
`bug_patch` by applying it with `git apply --check` in the sandbox and discarding anything
that fails.

### A3. CRITICAL — Nothing in the pipeline is actually verified

`PROGRESS_LOG.md` says "113 **Pristine** Teacher Trajectories", "high-density quality
filter", `sft_verified.jsonl`. The only filter in the code is:

```python
if msgs and len(msgs) >= 4:        # src/teacher_rollouts.py:131
```

Length ≥ 4. No patch is applied, no test is run, no tool call is executed. The teacher
*imagines* the tool outputs — the contents of `read_file`, the result of `edit_file`, the
subgraph JSON — and those hallucinated observations go straight into the training set.
`reproduction_test` is generated by the synthesiser and then silently dropped (never
written to the task record in Cell 7, never used anywhere).

**Fix.** Generate trajectories by *running the real agent loop against the real sandbox*,
not by asking the model to write a screenplay. Keep a rollout only if `submit_patch` was
actually called and the resulting diff applies and the repro test flips red→green. With
115 real tasks and N=8 sampling you should net a few hundred genuinely verified rollouts.

## B. The training code is broken independently of the data

### B1. CRITICAL — The model is never trained to emit the end-of-turn token

`notebooks/repographforge_clean_master.md`, Cell 6:

```python
in_assistant_turn = False
for i in range(len(input_ids)):
    if input_ids[i] == model_turn_id:                           # <|turn>
        in_assistant_turn = True
    elif input_ids[i] == turn_end_id and in_assistant_turn:     # <turn|>
        in_assistant_turn = False
    if not in_assistant_turn:
        labels[i] = -100
```

Two bugs in six lines:

1. **The end-of-turn token is always masked.** When `input_ids[i]` is the turn-end token,
   the flag flips to `False` *before* the masking check, so `labels[i] = -100` on exactly
   the token that terminates the assistant's turn. Across 3 epochs the model never once
   receives gradient on "stop here". At inference it therefore does not stop: it runs to
   `max_output_tokens` (1024, set in Cell 8), the harness gets a run-on blob instead of a
   clean terminated tool call, no tool call is parsed, and the turn is wasted. This is the
   mechanism behind every symptom in your log — "emitted tool calls as raw JSON text in a
   conversational message", "burned the turn budget", "completed without explicit
   submit_patch call".

2. **"Assistant-only masking" masks nothing.** `<|turn>` is the generic turn *opener*; the
   role token (`user` / `model`) comes after it. So the flag is set `True` at the start of
   every turn, including user and tool turns. The model is trained to generate the
   hallucinated tool observations and the user messages too — which is precisely how a
   model learns to write `[{'id': 'call_4', ...}]` as prose instead of invoking a tool.

The token names are also inconsistent across the repo: the notebook uses `<|turn>` /
`<turn|>`, while `src/teacher_rollouts.py:161` builds `<start_of_turn>{role}` /
`<end_of_turn>`. At most one of those is right. If `convert_tokens_to_ids` returns the
unk-id for a name that does not exist, the loop masks the *entire* sequence and you train
on pure `-100`.

**Fix.** Don't hand-roll this. Use the chat template's own offsets:

```python
rendered = tokenizer.apply_chat_template(msgs, tokenize=False)
enc = tokenizer(rendered, add_special_tokens=False, truncation=True, max_length=MAX_LEN,
                return_offsets_mapping=True)
labels = [-100] * len(enc["input_ids"])
# unmask each assistant span, INCLUSIVE of its terminating end-of-turn token
for start, end in assistant_char_spans(rendered):   # end = index AFTER the end-of-turn marker
    for i, (a, b) in enumerate(enc["offset_mapping"]):
        if a >= start and b <= end:
            labels[i] = enc["input_ids"][i]
```

Then assert before training:

```python
assert any(l != -100 for l in labels)
assert labels[-1] != -100 or True   # and spot-check: the eot token id IS present in labels
print(tokenizer.decode([i for i, l in zip(enc["input_ids"], labels) if l != -100]))
```

That last `print` is the single highest-value check in this whole pipeline. Run it on
three samples and read the output. It should be exactly the assistant turns, each ending
in the end-of-turn token, and nothing else.

### B2. HIGH — `max_length=1536` truncates the label off the end of the trajectory

Cell 6 sets `MAX_LEN = 1536`. A 4-turn agent trajectory that contains a subgraph dump, a
file read and a unified diff is routinely 3–6k tokens. Truncation is from the right, so
the part that gets cut is turn 3 (`edit_file`) and turn 4 (`submit_patch`) — the only two
turns you actually need the model to learn. Many training examples therefore end
mid-`read_file` with no submit anywhere in the labels.

`src/train_qlora.py` uses 4096, the notebook uses 1536, `train_rft.py` uses 1536 — pick one.

**Fix.** `MAX_LEN = 8192` (L4 has the memory at batch 1 with gradient checkpointing), and
*drop* rather than truncate any example that still overflows. Log how many you drop.

### B3. HIGH — The RFT stage has no masking at all, and its data contains zero tool calls

`train_rft.py` (Cell 11):

```python
tokens["labels"] = tokens["input_ids"].copy()   # full-sequence loss, no masking
```

Worse is what it trains *on*. Cell 10 builds the RFT examples as a 4-message conversation
where turn 2 is plain prose and the patch is pulled out with:

```python
m = re.search(r"```(?:diff|patch)?\n([\s\S]*?)```", text)
```

So the accepted "best-of-N" trajectories are **markdown fences, not tool calls**. RFT is
the *last* training stage, and it is explicitly teaching the model to answer with a
` ```diff ` block instead of calling `submit_patch`. This actively destroys the native
tool-calling behaviour that your SFT v2 note says you had working. If the holdout went
from "first autonomous ground-truth fix" to "near-zero submissions", this is the
regression.

Second problem: it trains on **4 examples** (the `V_graph` filter accepted 4/50) for 2
epochs at `grad_accum=2` — roughly 4 optimizer steps. The log notes grad norm 239.7 → 7.29
in 29 seconds. That is not alignment, that is 4 samples of noise overwriting a 112-sample
SFT.

Third: the judge is `"model": "main_lora"` — the *policy being trained* is grading its own
rollouts. `V_graph` vs `V_free` is being measured with a contaminated verifier.

**Fix.** Either (a) delete the RFT stage until SFT is healthy — it is strictly hurting you
right now — or (b) rebuild it so rollouts come from the real sandbox with real tool calls,
masking matches B1, acceptance uses the *base* model as judge plus actual test execution,
and you require ≥50 accepted trajectories before running the pass.

### B4. MEDIUM — Likely double-BOS

Both training scripts do:

```python
text = tokenizer.apply_chat_template(msgs, tokenize=False)   # template emits BOS
tokens = tokenizer(text, truncation=True, ...)                # add_special_tokens=True → BOS again
```

Gemma templates emit `<bos>` themselves. The second call prepends another one. Double-BOS
measurably degrades instruction-following on Gemma. Pass `add_special_tokens=False`, or
use `apply_chat_template(..., tokenize=True)` directly.

### B5. MEDIUM — `src/train_qlora.py` would crash on any dict-valued tool argument

Line ~140 calls `json.dumps(args)` but the module never does `import json`. Reachable
whenever `arguments` is a dict. (The notebook version does import it — but the two scripts
also disagree on whether `arguments` should be a dict or a JSON string, see C1.)

## C. Train/inference mismatch

### C1. HIGH — Four mutually incompatible tool-call serialisations in one repo

| Where | Format |
|---|---|
| `src/teacher_rollouts.py:158` | `<\|tool_call\|>call:name{args}<\|tool_call\|>` inside `<start_of_turn>model` |
| `src/rft_sampler.py:38-42` | `<thought>…</thought><tool_call>{"name":…,"arguments":{…}}</tool_call>` |
| notebook Cell 6 | real `tool_calls` dicts, `arguments` as a **dict**, via `apply_chat_template` |
| `src/train_qlora.py:146` | real `tool_calls` dicts, `arguments` as a **JSON string** |
| notebook Cell 10 (RFT) | no tool call at all — a ` ```diff ` fence |

Only one of these matches what vLLM + the ADK actually parse at eval time. Whichever
trajectories use the other four are teaching the model a format the harness will ignore.

**Fix.** Pick the ADK/vLLM native format, define it in exactly one helper function, and
have every producer call it. Then verify end-to-end: render one training example, feed the
rendered prefix to the served model, and confirm the harness parses the continuation as a
tool call.

### C2. HIGH — Training sequences contain no system prompt and no tool declarations

`apply_chat_template(standardized, tokenize=False)` is called with no `tools=` argument and
the trajectories carry no system message. At eval time the model receives the
anti-hesitation system prompt plus the full schemas for nine tools (`run_command`,
`read_file`, `edit_file`, `write_file`, `get_status`, `submit_patch`,
`get_code_neighbors`, `search_similar_code`, `get_code_subgraph`) — a context shape it has
never seen. At r=32/alpha=64/lr=2e-4 over 3 epochs on 112 samples, the adapter is strong
enough to override the base model's handling of that unseen shape.

**Fix.** Render training examples with the *exact* system prompt and the *exact* `tools=`
schema list the eval harness uses.

### C3. MEDIUM — `max_output_tokens: 1024` truncates patches

Cell 8 writes `configs/sampling.yaml` with `max_output_tokens: 1024`, while
`submission/agent.yaml` says `max_tokens: 4096`. A `submit_patch` call carrying a
multi-hunk diff exceeds 1024 tokens easily; the JSON argument is then cut mid-string, the
tool call fails to parse or applies a truncated diff, and the tests fail. This is a second
distinct path to "submitted but failed".

Also note `submission/agent.yaml` is in a different schema entirely (`model.adapter_path`,
`agent.max_turns`, `agent.system_prompt`) from the one Cell 8 writes (`name`, `model`,
`adapter`, `instruction`, `tools`). One of the two is dead config; make sure you know
which one the grader reads.

### C4. MEDIUM — The anti-hesitation prompt forbids the behaviour the task requires

```
1. MAX 1 FILE READ … STRICTLY FORBIDDEN from reading secondary helper files … or test files.
3. MANDATORY EDIT ON TURN 3: You MUST invoke `edit_file` immediately after reading …
4. IMMEDIATE SUBMISSION: As soon as `edit_file` succeeds, your next turn MUST be `submit_patch`.
```

This guarantees a blind patch: the agent must edit after a single read and submit without
ever running a test, even though `run_command` is declared. Your own manuscript (§RQ2,
`requests_7502`) documents that real tasks need a cross-file hop — which rule 1 forbids.
It was tuned to make *one* task (`requests_7505`) finish in 53s; it generalises badly.

**Fix.** Replace the prohibition with a budget: "You have N tool calls. Read at most 3
files. Before `submit_patch`, run the relevant test with `run_command` if budget remains."

### C5. LOW — The audit table over-counts submissions

Cell 15: `elif args == {} or fn.get("name") == "submit_patch": submitted = True`. Any tool
called with empty arguments (e.g. `get_status()`) counts as a patch submission. Your
"patch submission rate" is inflated; drop the `args == {}` clause.

## Recommended order of work

1. **B1** — fix the masking, and print the unmasked text for 3 samples before training
   anything. (~30 min, no GPU)
2. **A1** — stop training on the bug-introducing diff. (~30 min, no GPU)
3. **B2 / B4** — `MAX_LEN=8192`, drop-don't-truncate, `add_special_tokens=False`. (~10 min)
4. **B3** — delete the RFT stage for now. It is net-negative. (~5 min)
5. **C1 / C2** — one tool-call format, rendered with the real system prompt and `tools=`.
   (~2 h)
6. **C3 / C4** — `max_output_tokens` to 4096, replace the prompt prohibitions with a
   budget. (~20 min)
7. Retrain SFT only. Evaluate on the holdout. *Then* consider A2/A3 (grounded, verified
   trajectory collection) and only afterwards rebuild RFT.

Steps 1–4 and 6 cost almost no GPU time and address every observed symptom. I would not
spend quota on another full run until the step-1 `print` shows clean assistant-only spans
that end in the end-of-turn token.

## One note on the manuscript

`PROGRESS_LOG.md` and `paper/manuscript.md` describe the trajectories as "verified"/
"pristine" and the `V_graph` filter as validated against execution. Given A3 (no execution
anywhere in the pipeline) and B3 (the judge is the policy itself), those claims are not
supported by the code as written. The Table 1 verifier-alignment result is also measured
against a synthetic negative set where one of the two negative classes is a fixed
three-line string (`"diff --git a/fix.py b/fix.py\n+ # Handled edge case defensively\n+ pass"`,
Cell 4) — one third of the benchmark is a trivially detectable constant, which inflates
both verifiers' scores. Worth correcting before the paper-track submission.
